## 확인 문제 정답

### 1부

- **1-1.** 로그인 안 함 → **401**. 직원의 관리자 기능 요청 → **403** (누군지는 알지만 권한 없음).
- **1-2.** 사용자는 "서버가 고장났다" 고 오해하고 무엇을 고쳐야 할지 모릅니다. 운영자는 진짜 서버 오류와 단순 입력 실수를 구분할 수 없어 모니터링이 쓸모없어집니다.
- **2-1.** `GET /api/v1/projects/3/guides`, `GET /api/v1/guides/7/attachment` — 우리 `GuideController` 와 같습니다.
- **2-2.** 예: 버튼을 누르면 바로 비활성화(프런트, 편의), 서버에서는 요청마다 고유 키를 받아 같은 키는 한 번만 처리(멱등 키), 또는 DB 유니크 제약. 우리 업데이트 등록은 "같은 프로젝트 + 같은 버전" 유니크 제약이 이 역할을 합니다.
- **3-1.** `passwordHash`, 실패 횟수·잠금 시각 등 내부 값. 게다가 LAZY 필드가 있다면 직렬화 중 예외나 추가 쿼리가 날 수 있습니다.
- **4-1.** 세션이 서버 메모리에 있으므로 모두 사라져 **다시 로그인**해야 합니다. (세션을 DB·Redis 에 저장하면 유지할 수 있습니다.)
- **4-2.** CSRF (29장).

### 2부

- **5-1.** `RemoteUpdateBackendApplication` 의 `@ConfigurationPropertiesScan`.
- **6-1.** 저장소를 S3 로 바꿀 때 `UpdateService` 도 고쳐야 하고, 테스트에서 가짜 저장소로 바꿔 끼울 수 없습니다.
- **7-1.** 괄호 안의 `new ApiException(...)` 은 `orElseThrow` 를 부르기 **전에** 먼저 실행되므로, 값이 있어도 매번 예외 객체(스택 정보 포함, 비쌈)를 만듭니다. 람다로 넘기면 없을 때만 만듭니다.
- **8-1.** checked 예외라 기본 설정에서는 **롤백되지 않고 커밋**됩니다. 일부만 저장된 상태가 남을 수 있습니다.
- **9-1.** `includes()` 는 선언 순서로 비교하므로 `MANAGER` 가 `STAFF` 보다 위, `DEVELOPER` 보다 아래가 됩니다(의도와 맞는지 확인 필요). DB 에는 이름(`"DEVELOPER"`)으로 저장되므로 기존 데이터는 영향이 없습니다. ORDINAL 로 저장했다면 `DEVELOPER`(1) 가 `MANAGER` 로 바뀌는 사고가 났을 것입니다.
- **10-1.** 둘 다 같은 값(예: 5)을 읽고 각자 6 을 저장 → 한 번이 사라집니다 (갱신 손실). 이력 행을 추가하는 방식은 서로의 행을 건드리지 않아 이 문제가 없습니다.

### 3부

- **11-1.** `@SpringBootApplication` 이 있는 `com.onpoom.remoteupdate` 패키지 **아래**만 스캔하기 때문입니다.
- **12-1.** 같은 타입의 빈이 두 개라 어느 것을 넣을지 몰라 **시작이 실패**합니다. `@Primary` 나 `@Qualifier` 로 골라 주거나, 설정에 따라 하나만 등록되게 해야 합니다.
- **13-1.** 실행 **전**에 검사합니다. 실패하면 `AccessDeniedException` → 403 이고 메서드 본문(그리고 서비스)은 실행되지 않습니다.
- **14-1.** ① 환경 변수 `APP_SECURITY_LOGIN_LOCKDURATION=30m` (스프링은 환경 변수 이름을 소문자로 바꾸고 `_` 를 `.` 로 읽으며 `-` 는 빼고 비교하므로 `app.security.login.lock-duration` 에 연결됩니다. 더 쉬운 방법은 yml 에 `${LOCK_DURATION:15m}` 자리를 미리 만들어 두는 것) ② 실행 인자 `--app.security.login.lock-duration=30m`. (그 밖에 jar 옆에 `application.yml` 을 두는 방법도 있습니다.)
- **15-1.** 제목이 빈 요청 → ③ 의 `@Valid` 에서 400. CSRF 토큰이 없는 요청 → ② 필터 체인의 CSRF 검사에서 403 (컨트롤러까지 가지도 않음).
- **16-1.** `@RequestParam(required = false) Long projectId`. 날짜는 `@DateTimeFormat(iso = ISO.DATE) LocalDate from` 처럼 형식을 지정합니다 (`DownloadController` 참고).
- **17-1.** 안 됩니다. 프런트 검사는 개발자 도구나 직접 API 호출로 건너뛸 수 있습니다 (43장).
- **17-2.** SQL, 테이블 이름, 파일 경로, 라이브러리 버전 같은 내부 정보가 공격자에게 노출됩니다.

### 4부

- **18-1.** 프로젝트 이름을 바꾸면 모든 업데이트 행을 고쳐야 하고, 빠뜨리면 같은 프로젝트가 다른 이름으로 보이는 불일치가 생깁니다.
- **18-2.** 서로 다른 프로젝트가 같은 버전 번호(예: 1.0.0)를 쓸 수 없게 됩니다.
- **19-1.** 같은 시각의 행들은 DB 가 순서를 마음대로 정할 수 있어, 페이지를 넘길 때 같은 행이 두 번 나오거나 빠질 수 있습니다.
- **20-1.** 비밀번호가 틀리면 예외를 던지는데, 그 예외로 트랜잭션이 롤백되어 **실패 횟수 증가도 취소**되기 때문입니다.
- **22-1.** `ProjectResponse`(DTO)를 바꿔도 DB 와 무관합니다. 서비스가 끝난 뒤의 엔티티는 준영속 상태라(트랜잭션이 끝남) 바꿔도 **반영되지 않습니다**.
- **23-1.** 목록 1번 + 업데이트 최대 20번 + 프로젝트 최대 20번 = 최대 41번. (같은 업데이트·프로젝트는 영속성 컨텍스트가 한 번만 조회하므로 실제로는 더 적을 수 있습니다.)
- **24-1.** 어느 서비스에서든 `setRole(ADMIN)`, `setLockedUntil(null)`, `setPasswordHash("평문")` 처럼 규칙을 거치지 않고 값을 바꿀 수 있게 됩니다. 잠금 규칙·마지막 관리자 규칙이 쉽게 우회됩니다.
- **25-1.** `size=10000000` 으로 이력 전체를 한 번에 요청 → DB·메모리·JSON 변환 부담. 그래서 최대 100 으로 자릅니다.

### 5부

- **27-1.** `AuthorizationFilter` 의 URL 규칙(`/api/v1/admin/**` → ADMIN)에서 **403**.
- **28-1.** 해시는 되돌릴 수 없어 서버도 원래 비밀번호를 모릅니다. 대신 **비밀번호 초기화**로 새 임시 비밀번호를 발급하고, 사용자가 첫 로그인 때 바꾸게 합니다.
- **29-1.** CSRF 방어는 상태를 바꾸는 메서드(POST 등)만 검사합니다. 또 GET 은 링크 하나로 보낼 수 있고, `SameSite=Lax` 쿠키도 다른 사이트에서 링크를 눌러 **이동하는 GET** 에는 붙습니다. 악성 사이트의 링크를 누르는 순간 삭제가 실행됩니다.
- **30-1.** 요청에 `X-Forwarded-For: 사무실IP` 헤더를 직접 써서 보내면 사무실에서 접속한 것으로 인정됩니다.

### 6부

- **31-1.** 같은 이름의 파일이 서로 덮어써집니다. 또 Windows 에서 쓸 수 없는 글자(`:`, `*` 등)나 아주 긴 이름 때문에 저장이 실패할 수 있습니다.
- **32-1.** 전송 중에는 트랜잭션(DB 연결)을 열어 둘 수 없고, 서버는 브라우저가 파일을 끝까지 **저장했는지** 확실히 알 수 없습니다 (연결이 끊겨도 서버 쪽에서는 보낸 것처럼 보일 수 있음). 그래서 "다운로드를 시작한 기록" 으로 정의했습니다.
- **33-1.** `afterCommit`. 트랜잭션 안에서 보냈는데 나중에 롤백되면, 등록되지 않은 업데이트에 대한 메일이 이미 나간 뒤입니다. (메일 발송이 느리면 트랜잭션도 길어집니다.)

### 7~8부

- **37-1.** 직원으로 로그인한 세션으로 `POST /api/v1/projects/{id}/updates` → **403** 확인. 그리고 **DB 에 업데이트가 생기지 않았는지**, 저장소에 파일이 남지 않았는지도 확인하면 더 좋습니다.
- **43-1.** 안 됩니다. 메뉴를 숨겨도 주소를 직접 입력하거나 API 를 직접 호출하면 요청이 갑니다. 보안 판단은 항상 서버가 합니다.

## 다음에 공부할 것

이 프로젝트에서 **아직 쓰지 않았지만** 다음 단계에서 만나게 될 주제들입니다. 대략 추천 순서입니다.

| 주제 | 왜 | 이 책과의 연결 |
|---|---|---|
| **SQL 더 깊게** — 실행 계획(`EXPLAIN`), 인덱스 설계 | JPA 가 만든 SQL 이 왜 느린지 알 수 있음 | 18, 19, 41장 |
| **트랜잭션 격리 수준과 락** — 낙관적 락(`@Version`), 비관적 락 | 동시에 같은 데이터를 고칠 때 (10-1 의 갱신 손실 해결) | 10, 20장 |
| **Flyway 마이그레이션** | 2차 개발에서 바로 씀 | 26장, `Phase2-Spec/db/README.md` |
| **QueryDSL** | Specification 보다 복잡한 동적 쿼리를 타입 안전하게 | 25장 |
| **단위 테스트와 Mockito** | 서비스를 DB 없이 빠르게 테스트 | 34장 |
| **캐시** (스프링 캐시, Redis) | 자주 읽고 잘 안 바뀌는 데이터 | 21장 |
| **세션 저장소 분리** (Spring Session + Redis) | 서버를 여러 대로 늘릴 때 | 4장, 확인 문제 4-1 |
| **JWT 와 OAuth2** | 외부 서비스·모바일 앱과의 인증 | 4장, security-guide 3장 |
| **비동기 처리** (`@Async`, 메시지 큐) | 메일 발송처럼 오래 걸리는 일을 응답과 분리 | 33장 |
| **모니터링** (Spring Boot Actuator, 지표·헬스 체크) | 운영 중 상태를 숫자로 계속 보기 | 41장 |
| **Docker** | 실행 환경을 통째로 묶어 배포 | 38, 40장 |
| **Linux 서비스 운영** (systemd, 로그 확인) | 2차 개발의 Linux 지원 | 39, 42장 |

공부 팁:
- **공식 문서**를 먼저 보는 습관 — Spring, Hibernate 문서는 예제가 풍부하고 버전이 정확합니다. 블로그 글은 옛 버전 기준인 경우가 많습니다 (우리는 Spring Boot 4 / Jakarta 패키지).
- 새 개념을 배우면 **이 프로젝트에 작게 적용**해 보세요. 예: `UpdateInfo` 에 `@Version` 을 달고 두 브라우저에서 동시에 수정해 보기.
- 막히면 **로그와 SQL 로그부터** 봅니다. 대부분의 답은 거기 있습니다.
