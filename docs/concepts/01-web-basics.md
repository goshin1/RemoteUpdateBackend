# 1부. 웹의 기초

[← 목차](../backend-concepts.md) · [2부 →](02-java-basics.md)

백엔드 개발자가 하는 일을 한 문장으로 줄이면 **"HTTP 요청을 받아서 HTTP 응답을 돌려주는 프로그램을 만드는 것"** 입니다.
스프링도, JPA 도, 보안도 전부 이 한 문장을 잘 해내기 위한 도구입니다. 그러니 HTTP 부터 시작합니다.

---

## 1장. 클라이언트와 서버, 그리고 HTTP

### 이야기

영업 담당자가 브라우저 주소창에 `http://서버:8080/projects/3` 을 치면 화면이 뜹니다. 그 사이에 무슨 일이 일어날까요?
브라우저(**클라이언트**)가 서버에게 "이거 주세요" 라고 **요청**하고, 서버가 "여기요" 하고 **응답**합니다. 이 대화의 문법이 **HTTP** 입니다.

### 개념: HTTP 메시지는 그냥 글자다

HTTP 는 생각보다 단순합니다. 실제로 오가는 것은 아래 같은 **텍스트**입니다.

**요청** (브라우저 → 서버)

```http
PUT /api/v1/updates/12 HTTP/1.1          ← ① 시작줄: 메서드 + 경로 + 버전
Host: localhost:8080                      ← ② 헤더: "이름: 값" 여러 줄
Content-Type: application/json
Cookie: JSESSIONID=8F3A...; XSRF-TOKEN=c1d2...
X-XSRF-TOKEN: c1d2...
                                          ← ③ 빈 줄 (헤더 끝)
{"title":"알림 기능 추가","content":"..."}  ← ④ 본문(body)
```

**응답** (서버 → 브라우저)

```http
HTTP/1.1 200 OK                           ← 시작줄: 버전 + 상태 코드 + 설명
Content-Type: application/json
                                          
{"id":12,"version":"1.1.0","title":"알림 기능 추가", ...}
```

| 부분 | 역할 | 우리 프로젝트 예 |
|---|---|---|
| **메서드** | 무엇을 하려는지 (동사) | `GET` 조회, `POST` 생성, `PUT` 전체 수정, `PATCH` 일부 수정, `DELETE` 삭제 |
| **경로** | 무엇에 대해 (명사) | `/api/v1/updates/12` |
| **쿼리 문자열** | 경로 뒤 `?` 이후, 조건 전달 | `/api/v1/downloads?projectId=3&page=0` |
| **헤더** | 부가 정보 | `Content-Type`(본문 형식), `Cookie`, `Content-Disposition`(다운로드 파일 이름) |
| **본문** | 실제 데이터 | JSON, 업로드 파일(multipart), 다운로드 파일 |
| **상태 코드** | 결과 요약 (응답에만) | 아래 표 |

### 상태 코드 — 세 자리 숫자로 결과 말하기

앞자리만 봐도 의미가 갈립니다: **2xx 성공 / 3xx 다른 곳으로 / 4xx 요청한 쪽 잘못 / 5xx 서버 잘못**.

| 코드 | 의미 | 우리 API 에서 언제 |
|---|---|---|
| 200 OK | 성공 | 대부분의 조회·수정 |
| 201 Created | 새로 만들어짐 | 프로젝트·업데이트 등록 (`Location` 헤더에 새 주소) |
| 204 No Content | 성공, 돌려줄 본문 없음 | 로그아웃, CSRF 쿠키 발급 |
| 400 Bad Request | 입력이 잘못됨 | 제목이 비었음, 버전 형식 오류 |
| 401 Unauthorized | **누군지 모름** (로그인 필요) | 세션 만료, 비밀번호 틀림 |
| 403 Forbidden | **누군지는 알지만 안 됨** | 직원이 업데이트 등록 시도, 허용되지 않은 IP |
| 404 Not Found | 없음 | 없는 업데이트 번호 |
| 409 Conflict | 현재 상태와 충돌 | 같은 버전·이메일이 이미 있음 |
| 413 Payload Too Large | 너무 큼 | 500MB 넘는 파일 |
| 500 Internal Server Error | 서버 코드의 예상 못 한 오류 | (안 나야 정상) |

> 401 과 403 의 차이는 5부에서 "인증과 인가" 로 다시 나옵니다. 지금은 **401 = 너 누구야?, 403 = 너인 건 아는데 안 돼** 로 기억하세요.

### 직접 보기

브라우저에서 `F12` → **Network(네트워크)** 탭을 열고 RemoteUpdate 화면을 눌러 보세요. 요청 하나를 클릭하면 Headers / Payload / Response 탭에서 위의 모든 부분을 볼 수 있습니다. **백엔드 공부에서 가장 자주 쓰게 될 도구**입니다.

### 정리

- HTTP 는 요청 → 응답 한 번으로 끝나는 텍스트 대화다.
- 요청 = 메서드 + 경로 + 헤더 + 본문, 응답 = 상태 코드 + 헤더 + 본문.
- 상태 코드는 앞자리로 누구 잘못인지 알 수 있다 (4xx 요청 쪽, 5xx 서버 쪽).

### 확인 문제

1-1. 로그인하지 않은 사람이 `/api/v1/projects` 를 요청하면 몇 번 상태 코드가 와야 할까요? 직원이 `POST /api/v1/projects`(관리자 전용)를 요청하면요?
1-2. 사용자가 입력을 잘못해서 생긴 오류를 500 으로 응답하면 어떤 문제가 생길까요?

## 2장. REST API 설계 — 주소와 메서드로 말하기

### 이야기

API 주소를 아무렇게나 지으면 어떻게 될까요? `/getUpdate`, `/updateList`, `/doDisableUpdate`, `/update_delete_v2` ...
사람마다 규칙이 달라 매번 문서를 찾아봐야 합니다. **REST** 는 "주소는 명사(자원), 동작은 HTTP 메서드(동사)" 로 통일하자는 약속입니다.

### 개념

| 원칙 | 나쁜 예 | 좋은 예 (우리 API) |
|---|---|---|
| 주소는 **자원(명사)**, 복수형 | `/getProjects` | `GET /api/v1/projects` |
| 동작은 **메서드**로 | `/createUpdate` | `POST /api/v1/projects/3/updates` |
| 하나를 가리킬 땐 **ID** | `/update?id=12` | `GET /api/v1/updates/12` |
| 소속 관계는 **경로 중첩** | | `/projects/3/updates` (3번 프로젝트의 업데이트들) |
| 조건·페이지는 **쿼리 문자열** | `/downloads/project/3/page/2` | `/downloads?projectId=3&page=2` |
| 상태 변경은 하위 자원/PATCH | `/disableUpdate/12` | `PATCH /api/v1/updates/12/status` + `{"status":"DISABLED"}` |
| 버전을 주소에 | | `/api/v1/...` → 나중에 크게 바뀌면 `/api/v2` 를 따로 열 수 있음 |

### PUT 과 PATCH, 그리고 멱등성

- **PUT** = "이 자원을 이 내용으로 **바꿔라**" (보낸 값이 곧 결과). 업데이트의 제목·내용 수정 `PUT /updates/12`.
- **PATCH** = "이 부분만 바꿔라". 상태만 바꾸는 `PATCH /updates/12/status`.
- **멱등(idempotent)**: 같은 요청을 여러 번 보내도 결과가 같은 성질. `GET`, `PUT`, `DELETE` 는 멱등이어야 하고 `POST` 는 아닙니다 (두 번 보내면 두 개가 생김).
  네트워크가 끊겨 브라우저가 요청을 다시 보내도 안전한지가 여기에 달려 있습니다.
  우리는 이미 "중단" 상태인 업데이트를 또 "중단" 하면 **이력을 남기지 않게** 해서, 같은 요청을 반복해도 결과가 같게 했습니다 (`UpdateService.changeStatus` 의 `if (info.getStatus() != status)`).

### 응답 형식도 약속이다

- 성공: 자원을 JSON 으로 (`{ "id": 12, "version": "1.1.0", ... }`)
- 목록: 페이지 정보와 함께 (`{ "content": [...], "page": 0, "size": 20, "totalElements": 45, "totalPages": 3 }`) — 4부 25장
- 오류: **항상** `{ "code": "DUPLICATE_VERSION", "message": "이 프로젝트에 같은 버전이 이미 등록되어 있습니다." }` — 3부 17장

형식이 하나로 정해져 있으면 프런트는 오류 처리 코드를 한 번만 쓰면 됩니다 (8부 43장).

> 코드: Backend `README.md` 의 "API 요약" 표에 전체 API 가 있습니다.

### 정리

- 주소 = 명사(자원), 메서드 = 동사. 조건은 쿼리 문자열로.
- 같은 요청을 반복해도 안전한지(멱등성)를 생각하며 메서드를 고른다.
- 성공·목록·오류 응답의 모양을 처음부터 통일한다.

### 확인 문제

2-1. "3번 프로젝트의 가이드 목록" 과 "7번 가이드의 첨부 파일 받기" 를 REST 로 설계하면? (우리 코드의 `GuideController` 와 비교해 보세요)

## 3장. JSON 과 직렬화

### 이야기

서버의 데이터는 자바 **객체**인데, HTTP 로는 **글자**만 보낼 수 있습니다. 그래서 객체 → 글자(JSON)로, 글자 → 객체로 바꾸는 과정이 필요합니다.

- **직렬화(serialization)**: 객체 → JSON 글자 (응답 보낼 때)
- **역직렬화(deserialization)**: JSON 글자 → 객체 (요청 받을 때)

### 개념

```java
public record UpdateMetaRequest(String title, String content) { }
```
```json
{ "title": "알림 기능 추가", "content": "센서 이상 시 알림" }
```

스프링은 이 변환을 **Jackson** 라이브러리에 맡깁니다(우리는 Jackson 3, 패키지 `tools.jackson`). 컨트롤러가 객체를 돌려주면 Jackson 이 JSON 으로 바꾸고, `@RequestBody` 가 붙은 파라미터에는 JSON 을 객체로 바꿔 넣어 줍니다. 이 변환기를 스프링에서는 **HttpMessageConverter** 라고 부릅니다 (3부 15장).

| 자바 | JSON |
|---|---|
| `String`, `long`, `boolean` | 문자열, 숫자, true/false |
| `null` | `null` |
| `List<X>` | 배열 `[ ... ]` |
| record / 객체 | `{ "필드이름": 값 }` |
| enum `UpdateStatus.ACTIVE` | `"ACTIVE"` |
| `LocalDateTime` | `"2026-10-04T21:34:00"` (ISO-8601 형식) |

### 주의할 점

1. **필드 이름이 곧 API 다.** record 필드 이름을 `title` → `subject` 로 바꾸면 프런트가 깨집니다. 그래서 엔티티를 그대로 내보내지 않고 응답 전용 DTO 를 둡니다 (3부 17장).
2. **모르는 필드가 오면?** 요청 JSON 에 `"developerId": 1` 같은 필드를 몰래 넣어도, DTO 에 그 필드가 없으면 그냥 무시됩니다. 그래서 "받으면 안 되는 값"은 DTO 에서 **빼 버리는 것**이 가장 확실한 방어입니다.
3. **JSON 을 DB 에 저장할 수도 있다.** 업데이트 변경 이력은 수정 전·후 상태를 JSON 문자열로 저장합니다. `UpdateService.toJson()` 이 `JsonMapper` 로 직접 직렬화하고, 화면에 줄 때 `parse()` 로 다시 읽습니다.

> 코드: `update/UpdateSnapshot.java`(이력에 남길 필드만 모은 record), `UpdateService.toJson()`

### 정리

- 객체 ↔ JSON 변환을 직렬화/역직렬화라고 하고, 스프링에서는 Jackson 이 한다.
- DTO 의 필드 이름과 모양이 곧 API 계약이다.

## 4장. HTTP 는 기억하지 못한다 — 쿠키와 세션

### 이야기

HTTP 는 **무상태(stateless)** 입니다. 요청 하나하나가 독립적이라, 서버는 방금 로그인한 사람이 다음 요청을 보낼 때 그 사람인지 **알 방법이 없습니다**.
매 요청마다 아이디·비밀번호를 보낼 수는 없으니, "번호표" 를 주고받기로 합니다.

### 개념: 쿠키 = 브라우저가 들고 다니는 번호표

1. 서버가 응답 헤더로 `Set-Cookie: JSESSIONID=8F3A...` 를 보냅니다.
2. 브라우저는 이 값을 저장하고, **같은 서버로 가는 모든 요청에 자동으로** `Cookie: JSESSIONID=8F3A...` 를 붙입니다.

### 개념: 세션 = 서버가 번호표로 찾는 사물함

서버는 메모리에 "사물함" 을 두고 번호표(세션 ID)로 찾습니다.

```
브라우저                              서버 메모리 (세션 저장소)
Cookie: JSESSIONID=8F3A...   ──▶     8F3A... → { 로그인 사용자: 김개발, 역할: DEVELOPER }
                                      91BC... → { 로그인 사용자: 이영업, 역할: STAFF }
```

- 로그인에 성공하면 서버가 사물함에 사용자 정보를 넣고 번호표를 줍니다.
- 이후 요청은 번호표로 사물함을 열어 "누구인지" 압니다.
- 30분 동안 요청이 없으면 사물함을 비웁니다 (`server.servlet.session.timeout: 30m`) → 다음 요청은 401.
- 로그아웃하면 사물함을 비우고 쿠키도 지웁니다.

### 쿠키 옵션 — 번호표 보호 장치

번호표를 훔치면 그 사람인 척할 수 있으므로 보호가 중요합니다. `application.yml` 에 설정해 두었습니다.

| 옵션 | 의미 | 우리 설정 |
|---|---|---|
| `HttpOnly` | 자바스크립트로 읽을 수 없음 → 화면에 악성 스크립트가 끼어들어도(XSS) 훔칠 수 없음 | `true` |
| `SameSite=Lax` | 다른 사이트에서 시작된 POST 요청에는 쿠키를 붙이지 않음 | `lax` |
| `Secure` | HTTPS 연결에서만 보냄 | 운영에서 HTTPS 면 `true` (`COOKIE_SECURE`) |

### 세션의 반대편: 토큰(JWT)

번호표 대신 "서명된 신분증" 을 주는 방식도 있습니다. 서버는 사물함 없이 서명만 확인하면 되므로 서버가 여러 대일 때 편합니다. 대신 **한번 준 신분증을 중간에 무효로 만들기 어렵습니다**.
우리는 사내 시스템이고 서버가 한 대이며, "계정을 중지하면 바로 막혀야 한다" 가 중요해서 세션을 골랐습니다 (자세한 비교: [security-guide.md 3장](../security-guide.md#3-세션--쿠키-로그인)).

> 코드: `auth/SessionAuthenticator.java`(로그인 시 세션에 사용자 저장), `application.yml` 의 `server.servlet.session`

### 정리

- HTTP 는 이전 요청을 기억하지 못한다(무상태).
- 쿠키는 브라우저가 자동으로 들고 다니는 값, 세션은 서버가 그 값으로 찾는 저장 공간.
- 쿠키에는 HttpOnly · SameSite · Secure 같은 보호 옵션을 건다.
